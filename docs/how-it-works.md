# How Qwen3.8 Flash Next works with vLLM

## How the model works

Suppose you send “I left the key on the kitchen” and ask the model to continue. A **tokenizer** splits the text into pieces and assigns each piece an integer ID. A piece can be a word, part of a word, punctuation, or whitespace. The ID is an address. Looking it up in a table gives the model an **embedding**, a list of 2,560 learned numbers. The table and the other learned numbers in the checkpoint are its **weights**. They stay fixed throughout the conversation. The numbers computed *from* your prompt, including the representation of “kitchen” and the record of what preceded it, are request-specific **state**. Two requests can share the weights and produce very different states. [Qwen model overview](https://huggingface.co/Qwen/Qwen3.8-Flash-Next#model-overview) · [Pinned configuration](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-NVFP4/blob/fc694b54fb0174e0913e6adf86691ef85a4ead47/config.json)

To generate the next piece, the model transforms each input embedding through 48 layers. By the last layer, the vector at the final position depends on the entire sequence of computations leading there. A separate learned matrix called the **language-model head** converts that vector to 248,320 scores, one for each row of the padded vocabulary. Turning eligible scores into probabilities is called *softmax*. For illustration, “ counter” might have probability 0.55 and “ table” 0.30, with 0.15 spread across other possibilities. A greedy decoder picks the highest score. A sampling decoder draws from the distribution after applying the request’s sampling settings. If it emits “ counter”, that ID becomes an input for the next step. These example probabilities illustrate the decision and are independent of the benchmark. [Qwen model overview](https://huggingface.co/Qwen/Qwen3.8-Flash-Next#model-overview) · [Pinned configuration](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-NVFP4/blob/fc694b54fb0174e0913e6adf86691ef85a4ead47/config.json)

### Follow the final prompt token

```text
token IDs -> 2,560 numbers per token -> four residual branches
            layer 2 also reads short token sequences from a learned table
            12 groups of four layers, each with its own weights
                3 × (Gated DeltaNet -> mixture of experts)
                1 × (Qwen Sparse Attention -> mixture of experts)
            final representation -> vocabulary scores -> next token ID
```

**How a phrase gets a representation of its own.** The input embedding for “kitchen” starts the same wherever that token ID appears. At layer 2, a per-layer embedding (PLE) lookup also uses adjacent **n-grams**, sequences of token IDs ending at this position. Assuming one token per word for this example, “the kitchen” provides a bigram and “on the kitchen” a trigram. Their IDs determine table addresses before deeper layers run. The model reads the selected vectors and incorporates the local phrase information into that position. The nominal n-gram vocabulary is 20 million and the tables add about 51 billion parameters. Each position needs only its selected rows. Reading those rows in advance can overlap the lookup with other work. [Qwen on n-gram embeddings](https://arxiv.org/html/2608.30320v1#S2.SS3) · [Checkpoint settings](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-NVFP4/blob/fc694b54fb0174e0913e6adf86691ef85a4ead47/config.json)

**What carries a feature from layer to layer?** A residual connection lets a layer add an update to information already present. Flash Next maintains four 2,560-number branches per token. Before each token mixer or expert sublayer, Gated Residual normalizes each branch and calculates read weights from their contents through a 320-wide intermediate projection. The read weights can differ for each branch and each coordinate. The sublayer receives one combined vector and computes one update. A separate learned gate sets how much of that update to add back to each branch, using one scalar per branch. A feature can therefore remain strong on one branch while later layers choose a different mixture to read. These four branches belong to one token in one request. [Qwen’s Gated Residual design](https://arxiv.org/html/2608.30320v1#S2.SS2) · [Pinned configuration](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-NVFP4/blob/fc694b54fb0174e0913e6adf86691ef85a4ead47/config.json)

**How the first three layers in a group remember preceding text.** A Gated DeltaNet (GDN) layer maintains a matrix of associations for each recurrent value head. From the current vector it computes a query, a key and a value. In plain terms these are a question to ask of memory, an address for an update and information to store. A short learned filter blends features from up to four consecutive positions. The layer decays some previous state, looks up what the key already predicts, and writes a gated correction toward the new value. Its query reads the updated state to produce this token’s output. For example, “counter” later in a sentence can change an earlier association between a key and a location. Real addresses are learned vectors, so multiple associations can interact. The 36 GDN layers use 16 query/key heads and 48 value heads, each 128 numbers wide. Their main recurrent matrices stay the same size as a conversation grows. [Qwen on the gated delta update](https://arxiv.org/html/2608.30320v1#S2.SS1.SSS1) · [Checkpoint dimensions](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-NVFP4/blob/fc694b54fb0174e0913e6adf86691ef85a4ead47/config.json)

**How the fourth layer can retrieve an old detail.** Qwen Sparse Attention (QSA) keeps token-level keys and values from earlier positions. Suppose the prompt contains thousands of lines and one identifies the key’s owner. The current position first scores summaries of complete four-token blocks. The indexer averages keys within each block and uses four 128-wide query heads with one shared key head. It ranks the blocks, selects up to 512 and expands them back into individual positions. The main attention reads the selected tokens’ original keys and values, so a token can contribute differently from its neighbors. The published rule also includes the current incomplete block. The 2,048-token budget describes the selected complete-block content. The indexer can find a remote block even if many tokens have arrived since. It can also overlook one. [Qwen’s QSA selection rule](https://arxiv.org/html/2608.30320v1#S2.SS1.SSS2)

Each of the 12 QSA layers has 24 main query heads sharing two key/value heads. A *head* is one set of projections that can learn a different way of matching features. The main heads are 256 numbers wide. Rotary position embeddings rotate 64 coordinates according to position, giving the matching calculation information about where tokens appeared. Selected positions receive normalized attention weights, and their weighted values form the layer’s retrieval result. The indexer reduces how much detailed attention to compute at a given step. Older keys and values must remain accessible because a different question can select different blocks. [Qwen architecture report](https://arxiv.org/html/2608.30320v1#S2.SS1.SSS2) · [Qwen model overview](https://huggingface.co/Qwen/Qwen3.8-Flash-Next#model-overview)

**What happens after every memory read.** A mixture of experts (MoE) transforms each position’s updated features. There are 512 routed expert networks per layer. A small router scores them for this input and selects ten. Each selected expert projects through an intermediate width of 640, applies a learned gated transformation and returns an update in the language model’s width. Their weighted outputs join the contribution of a shared expert that runs for every token. The next position can select a different ten. Qwen counts 125 billion parameters in the main model with about six billion active per token, then reports the 51 billion n-gram parameters and four billion multi-token prediction parameters separately. Sparse routing saves arithmetic while the engine still needs access to the pool of possible experts. The final read from the branches reaches the output head described above. [Qwen model overview](https://huggingface.co/Qwen/Qwen3.8-Flash-Next#model-overview) · [Pinned configuration](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-NVFP4/blob/fc694b54fb0174e0913e6adf86691ef85a4ead47/config.json)

**Where images and drafts enter.** Images take a different route into the same language layers. A 27-layer vision encoder with width 1,152 and 16 attention heads reads 16-by-16-pixel patches. Its configuration groups two time slices per temporal patch and merges 2-by-2 groups spatially. A projection produces 2,560-wide visual features that fill visual positions in the prompt. The output is still a sequence of text tokens. At the other end, a separately trained, single-layer **multi-token prediction** (MTP) module uses model features and token embeddings to propose subsequent IDs. Its proposals can accelerate generation when checked together by the main model. Qwen’s architecture illustration describes reuse of QSA index selections across draft iterations. The engine determines how that part executes on the Spark. [Vision and MTP configuration](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-NVFP4/blob/fc694b54fb0174e0913e6adf86691ef85a4ead47/config.json) · [Qwen architecture, figure 1](https://arxiv.org/html/2608.30320v1#S1)

## How this recipe runs it on one DGX Spark

### From the download to a resident server

A DGX Spark has one GB10 with a memory pool shared by its CPU and GPU. Expert routing reduces work for each token, but a different token can select another expert, so the full model must remain accessible. A second opportunity comes from the n-gram table. The prompt IDs tell the CPU exactly which rows will be needed, and the GPU needs only the resulting features. This recipe uses that property to serve the NVIDIA NVFP4 checkpoint at `fc694b54fb0174e0913e6adf86691ef85a4ead47` with one GPU and a host-side PLE worker. [NVIDIA checkpoint](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-NVFP4/blob/fc694b54fb0174e0913e6adf86691ef85a4ead47/README.md) · [Observed runtime](../README.md#runtime)

The checkpoint is a *mixed-precision* export. Quantization represents a group of numbers on a smaller set of levels using a shared scale. Here the decoder’s routed expert matrix multiplications use four-bit floating-point weights and activations (NVFP4 W4A4). The scale groups have 16 weights. Main attention and shared experts retain BF16, a 16-bit floating-point format. The draft module’s routed experts use block-scaled FP8, and the PLE table uses eight-bit floating-point storage. Runtime FP8 KV is another choice that applies to the saved history of each request. Lower precision can shift probabilities relative to the original checkpoint. The target for this recipe is the particular NVIDIA export, distinct from the FP4-Local export used in some other Spark builds. [NVIDIA precision map](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-NVFP4/blob/fc694b54fb0174e0913e6adf86691ef85a4ead47/README.md) · [Pinned layer settings](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-NVFP4/blob/fc694b54fb0174e0913e6adf86691ef85a4ead47/config.json)

`serve.sh download` checks out Mia’s launcher at `b7c5da1a9e7448a14b480deee66eda3799b1eb43`, pulls an ARM64 vLLM image by digest and downloads the public NVIDIA snapshot into the dedicated cache under `~/.cache/spark-flash-next-vllm`. An offline reference points to that exact snapshot. The recipe chose the public export after the original Mia checkpoint returned HTTP 401 during staging. `start` verifies the revision and presence of the materialized shard, then invokes upstream’s start script. That script prepares a packed PLE file on first use. A 123.57 GiB snapshot plus another packed copy of the table explains the estimate of roughly 175 GiB of disk space before the image. Initial service startup took 752 seconds after packing. Later inference timings start with the model resident. [Local launcher](../serve.sh) · [Upstream startup code](https://github.com/MiaAI-Lab/Qwen3.8-Flash-Next-Single-DGX-Spark/blob/b7c5da1a9e7448a14b480deee66eda3799b1eb43/start.sh) · [Staging and measurements](../README.md#runtime)

The CPU offload worker memory-maps the 47.68 GiB packed table. Mapping associates file offsets with virtual addresses so the operating system can bring a page into memory when accessed. The file’s disk size, its mapped address range and its resident pages describe different things. The active language layers run on the GPU. The launcher budgets 2.34 GiB for MTP weights and reserves 30 GiB on the host side. The test sampled a peak of 87.6 GiB across GPU processes in the inference container and a 101.0 GiB Docker memory limit. On unified memory, summing those two figures or adding the entire mapped file to either figure would double-count or mix incompatible measures. ### How the server handles an incoming question

The client posts messages to the loopback server at `127.0.0.1:18897/v1/chat/completions` with model ID `Qwen3.8-Flash-Next-vLLM`. The chat template inserts role boundaries and the generation prompt. During **prefill**, vLLM processes the prompt’s IDs, fetching phrase embeddings and building GDN recurrent state and QSA token-level KV caches. Chunked prefill lets the scheduler divide a long input into smaller pieces that fit a scheduling step. During **decode**, the scheduler groups active sequences for the next piece of computation. Each request keeps its own cache and sequence position. The upstream launcher configures decode-only CUDA graphs. A graph is a reusable GPU execution plan for a given batch shape. It saves repeated launch setup for matching shapes. The receipts record end-to-end times across that whole path. [Local request client](../benchmark.py) · [Pinned scheduler and graph options](https://github.com/MiaAI-Lab/Qwen3.8-Flash-Next-Single-DGX-Spark/blob/b7c5da1a9e7448a14b480deee66eda3799b1eb43/start.sh)

MTP ×3 means the trained draft module can propose a chain of three follow-on IDs. A verified round can advance multiple positions because the target can score all proposed positions together, with each candidate conditioned on the prefix before it. In a greedy example, if the draft suggests “counter by noon” and the target first disagrees on “noon”, the agreeing “counter by” can be committed and the target supplies the next token. The suffix after a disagreement has lost its assumed prefix. Standard speculative sampling uses a target-correct acceptance and replacement rule to preserve the distribution of the serving target. The recipe’s timing sweep includes sampling but contains no distributional parity test. The observed QSA backend rebuilt attention metadata between draft steps, so index reuse described by Qwen’s reference design cannot be assumed for this run. ### Reading the concurrency and context measurements

The 262,144-token context setting limits each request’s prompt plus permitted continuation. The scheduler can have up to five sequences in flight. vLLM reported an FP8 cache of **8.12 GiB for 488,656 token positions across the engine**. Even two entirely separate full windows would require 524,288 positions before accounting for sharing and allocation details. Five short chats fit a different workload than five full-window chats. The growing cost comes from the QSA token records and serving metadata. Each GDN matrix has fixed dimensions but still needs a distinct current state for each active sequence. [Runtime measurements](../README.md#runtime) · [Model dimensions](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-NVFP4/blob/fc694b54fb0174e0913e6adf86691ef85a4ead47/config.json)

The direct streaming benchmark used a short hash-map explanation prompt with thinking enabled and 400 generated tokens per stream. Temperature 0.7 scales the output scores, top-k 20 keeps at most twenty candidates and top-p 1 applies no further probability-mass cutoff. One through five streams reached **29.8, 43.7, 59.5, 76.5 and 78.8 aggregate tokens/s**, using the fastest of three waves at each concurrency. The single stream delivered 29.8 tokens/s after a 403 ms time to first token (TTFT). At five streams the same wave had median 17.1 tokens/s per reader and median TTFT of 836 ms. The shared decode interval begins at the first streamed reasoning or answer token and ends at the last stream’s final token. Extra throughput across users therefore coexists with a slower response for an individual reader. [Benchmark code](../benchmark.py) · [Decode results](../results/benchmark-2026-11-21.json)

In separate single-request tests the server reported zero cached prompt tokens. A 32,740-token prompt reached its first token after 18.58 seconds, or **1,763 input tokens/s**. A 199,952-token prompt took 114.63 seconds, or **1,744 input tokens/s**. Each contained a newly generated key that the model returned exactly. Input tokens divided by *client TTFT* includes client and server overhead. This rate measures the wait to begin a reply and uses a different numerator and clock than output decode. Both tests exercised text over localhost. The checkpoint supports visual inputs at the model level, while the local receipts cover prose generation and these two retrieval prompts.
